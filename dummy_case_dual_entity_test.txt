1. BACKGROUND

A complaint was filed regarding a suspected shell-company fraud
operation. During investigation, officers identified a recurring name,
"Solapur", which appears in the case both as a place reference and,
separately, as a person's surname — this is a deliberately ambiguous
case designed to test whether the extraction system can distinguish
context correctly rather than merging both meanings under one ID.

Investigating officers first encountered the term "Solapur" as a city
reference: several fraudulent transactions were routed through a
shell company registered in Solapur, Maharashtra.

Later in witness statements, officers recorded a statement from a man
identified only by his surname, Solapur, who claimed to be a former
employee of the shell company and provided information about its
internal structure.

NOTE FOR TESTING PURPOSES:
This is a synthetic/fictional document with no real persons or events.
It is designed specifically to test two known bugs:
1. The same text ("Solapur") appearing legitimately as both a
   LOCATION and a PERSON surname in different contexts — the system
   should NOT assign both types to the same entity_id; it should
   either correctly disambiguate by context or, at minimum, assign
   two clearly DIFFERENT entity_ids for the two distinct real-world
   referents, never reuse one ID across two types.
2. Table-style person records (ID | Name | Age | Relationship) should
   extract ONLY the Name column as the PERSON entity value — age and
   relationship-description text should never be concatenated into
   the entity name itself (e.g., must not produce a garbled entity
   like "Reshma Solapur 29 Company director's relative").
